## What's new

**In short:** two serious security holes are closed: a forged message could mark an order as paid, and a backup changed where it is kept could run commands on the server. Everything else an independent security review found is fixed too. The end of this note lists what to check on your server.

### Security
- **A payment message without a valid signature no longer touches an order.** Anyone could send one to the shop's payment address, and the order could count as paid with no money received. Such a message now only leaves a line in the payment log.
- **This update removes the payments such messages created.** The order's amounts are recalculated and its history gets the line "A payment no gateway confirmed was removed". Its status and stock stay as they are.
- **A backup changed where it is kept is refused.** Before restoring or checking a backup, the shop compares it with the checksum recorded when it was made. An encrypted backup can no longer be replaced with an unencrypted file.
- **Restoring a backup in plain SQL now runs SQL only.** Commands for `psql` hidden in the file could start programs on the server.
- **monobank:** a bad signature made the shop ask the bank for its key every time. Now it asks at most once in 10 minutes.
- **monobank:** an invoice this shop did not create can no longer change an order.

### Payments and refunds
- **A payment for less than the invoice no longer counts as paid in full.** The order shows the money that really came, and the goods wait for the rest. A sum in a currency nobody asked for is not counted at all.
- **Each payment method's messages are checked with its own keys.** This matters if one gateway has a test and a live account, or accounts of two companies.
- **A refund the bank refused is no longer written down as made,** and a double click no longer refunds twice.

### Accounts and letters
- **Changing a password now ends everything opened with the old one:** other browsers, "Remember me", unused password links and invitations. It does not matter how the password was changed.
- **One address, one account.** `Anna@example.com` and `anna@example.com` are now the same address.
- **A code works once,** even when several requests with it arrive at the same moment.
- **The button in a code letter now opens a page with one more button.** Mail filters open the links in a letter, and that used up the code before the customer got there. "Stop these letters" in wishlist letters works the same way now.
- **Links in letters always lead to your shop.** A forged request could make the shop send a real password letter whose button led to another site.

### Limits
- **The limits of different forms no longer add up.** A few background requests from a browser could close the lost-password form for everyone on that address.
- **API:** a made-up key no longer gets a limit of its own, and a switched-off storefront is not served.
- **Coupons and gift cards:** 10 wrong codes a minute from one address, on the site and in the API.
- **Files attached to a product option:** up to 60 an hour from one address.
- **Quantity in a basket:** up to 1,000,000 in one line. A huge number broke the basket.
- **Pictures by link:** up to 20 at a time, and a download stops at the size limit instead of being read to the end.

### Other
- **1C exchange:** one account cannot touch another's exchange, a file that would leave less than 1 GB free on the disk is refused, and exchange files are removed after 7 days. They used to stay forever.
- **Installer:** the database check asks for the installer's code, and the page no longer shows the server's folders.
- **A backup folder where the web server hands out files is refused.** Anyone could have downloaded a backup from there.
- **A text can no longer cover the page.** Descriptions, pages and articles stay inside their own block.
- **An update is downloaded only from the address of the update server.**
- **The "Page" line of an enquiry** is a link only when it is a real address.

### Backups
- **An interrupted "Check by restoring" no longer leaves a copy of the shop behind.** If a restart cut the check off, the next check deletes the database it left, and the unpacked files it left go after two days.

**After updating:** if any payments were removed, open the Errors screen in the Security section: the message lists the order numbers (they are also in `storage/logs/laravel.log`). Check whether those orders were shipped.

**Also after updating:**
- If one address was on two accounts in different capitals, one of them lost it: staff keep it first, then a confirmed address, then the older account. The account can still sign in by phone. The Errors screen lists these accounts.
- Buttons in code letters sent before the update stop working. A code lives 10 minutes, so ask for a new one.
- If the shop is opened at an address it does not know, its links now lead to the main address. Add that address on the Storefronts screen, in Domains.
- If your shop confirms contacts at checkout, orders through the API are refused with a message, because the API cannot ask for a code.

### Worth checking on your server
The update cannot do this for you.
- **PostgreSQL version: 18.6, 17.11, 16.15, 15.19 or newer.** Older versions have a security flaw in `psql`, the program that restores SQL dumps. PostgreSQL does not update together with Torgash, and if it came from PostgreSQL's own repository, your system's automatic updates may not cover it.
- **The shop's database user must not be a superuser.** A superuser can start programs on the server with plain SQL. The user needs only the right to create databases (`CREATEDB`), for "Check by restoring".
- **Restoring an SQL dump from a file or on a new server** needs `psql` 15.14, 16.10, 17.6, 18 or newer. An older one refuses such a file.
- **Backups in the "No archive — a folder of files" format:** only the database inside is checked for changes. If others can write to the storage where one is kept, do not put modules and themes back from it (`--code`).

## Что нового

**Главное:** закрыты две серьёзные уязвимости: поддельное сообщение могло отметить заказ оплаченным, а резервная копия, изменённая там, где она хранится, могла запустить команды на сервере. В конце заметки сказано, что проверить на своём сервере.

### Безопасность
- **Сообщение о платеже без верной подписи больше не влияет на заказ.** Его мог отправить любой на платёжный адрес магазина, и заказ мог считаться оплаченным, хотя денег не было. Теперь от такого сообщения остаётся только строка в журнале платежей.
- **Платежи, созданные такими сообщениями, это обновление удаляет.** Суммы заказа пересчитываются, в истории заказа появляется строка «Удалён платёж, который не подтвердил ни один шлюз». Статус и остатки не меняются.
- **Копия, изменённая там, где хранится, отклоняется.** Перед восстановлением и проверкой магазин сравнивает её с контрольной суммой, записанной при создании. Зашифрованную копию больше нельзя заменить незашифрованным файлом.
- **Восстановление копии в формате SQL теперь выполняет только SQL.** Команды для `psql`, спрятанные в файле, могли запустить программу на сервере.
- **monobank:** при неверной подписи магазин каждый раз запрашивал у банка ключ. Теперь не чаще раза в 10 минут.
- **monobank:** счёт, созданный не этим магазином, больше не может изменить заказ.

### Платежи и возвраты
- **Оплата меньше суммы счёта больше не считается полной.** В заказе видно, сколько денег действительно пришло, и товар ждёт остальное. Сумма в валюте, которую никто не запрашивал, не засчитывается вообще.
- **Сообщения каждого способа оплаты проверяются его собственными ключами.** Это важно, если в одном шлюзе есть тестовый и боевой счета или счета двух компаний.
- **Возврат, в котором банк отказал, больше не записывается как сделанный,** а двойной клик больше не возвращает деньги дважды.

### Аккаунты и письма
- **Смена пароля теперь завершает всё, что было открыто со старым:** другие браузеры, «Запомнить меня», неиспользованные ссылки на смену пароля и приглашения. Как именно сменили пароль, неважно.
- **Один адрес, один аккаунт.** `Anna@example.com` и `anna@example.com` теперь один и тот же адрес.
- **Код работает один раз,** даже если несколько запросов с ним приходят одновременно.
- **Кнопка в письме с кодом теперь открывает страницу с ещё одной кнопкой.** Почтовые фильтры открывают ссылки в письме, и код сгорал раньше, чем до него добирался покупатель. «Отписаться от этих писем» в письмах об избранном теперь работает так же.
- **Ссылки в письмах всегда ведут в ваш магазин.** Поддельный запрос мог заставить магазин отправить настоящее письмо о смене пароля с кнопкой на другой сайт.

### Ограничения
- **Ограничения разных форм больше не складываются.** Несколько фоновых запросов браузера могли закрыть форму восстановления пароля всем с этого адреса.
- **API:** выдуманный ключ больше не получает отдельный лимит, а выключенная витрина не обслуживается.
- **Купоны и подарочные карты:** 10 неверных кодов в минуту с одного адреса, на сайте и в API.
- **Файлы к опции товара:** до 60 в час с одного адреса.
- **Количество в корзине:** до 1 000 000 в одной строке. Огромное число ломало корзину.
- **Картинки по ссылке:** до 20 за раз, а загрузка останавливается на лимите размера и не читается до конца.

### Другое
- **Обмен с 1С:** один аккаунт не может трогать обмен другого, файл, после которого на диске останется меньше 1 ГБ, отклоняется, а файлы обмена удаляются через 7 дней. Раньше они оставались навсегда.
- **Установщик:** проверка базы требует код установщика, а страница больше не показывает папки сервера.
- **Папка для копий там, откуда веб-сервер отдаёт файлы, отклоняется.** Копию оттуда мог бы скачать кто угодно.
- **Текст больше не может закрыть собой страницу.** Описания, страницы и статьи остаются в своём блоке.
- **Обновление скачивается только с адреса сервера обновлений.**
- **Строка «Страница» в обращении** становится ссылкой, только если это настоящий адрес.

### Резервные копии
- **Прерванная «Проверка восстановлением» больше не оставляет копию магазина.** Если проверку оборвал перезапуск, следующая проверка удалит оставшуюся базу, а распакованные файлы удалятся через двое суток.

**После обновления:** если платежи были удалены, откройте экран «Ошибки» в разделе «Безопасность»: в сообщении указаны номера заказов (они есть и в `storage/logs/laravel.log`). Проверьте, не отправлены ли эти заказы.

**Ещё после обновления:**
- Если один адрес был у двух аккаунтов в разном регистре, один из них его потерял: первыми адрес сохраняют сотрудники, затем подтверждённый адрес, затем более старый аккаунт. Войти по телефону этот аккаунт по-прежнему может. Такие аккаунты перечислены на экране «Ошибки».
- Кнопки в письмах с кодом, отправленных до обновления, перестают работать. Код живёт 10 минут, так что запросите новый.
- Если магазин открыт по адресу, которого он не знает, его ссылки теперь ведут на основной адрес. Добавьте этот адрес на экране «Витрины», в поле «Домены».
- Если ваш магазин подтверждает контакты при оформлении, заказы через API отклоняются с сообщением, потому что API не может запросить код.

### Что проверить на своём сервере
Обновление не может сделать это за вас.
- **Версия PostgreSQL: 18.6, 17.11, 16.15, 15.19 или новее.** В более старых есть уязвимость в `psql`, программе, которая восстанавливает дампы SQL. PostgreSQL не обновляется вместе с Torgash, а если он установлен из собственного репозитория PostgreSQL, автоматические обновления системы могут его не затрагивать.
- **Пользователь базы магазина не должен быть суперпользователем.** Суперпользователь может запускать программы на сервере обычным SQL. Пользователю нужно только право создавать базы (`CREATEDB`) для «Проверки восстановлением».
- **Восстановление дампа SQL из файла или на новом сервере** требует `psql` 15.14, 16.10, 17.6, 18 или новее. Более старый такой файл отклонит.
- **Копии в формате «Без архива — папка с файлами»:** на изменения проверяется только база внутри. Если в хранилище, где лежит такая копия, могут писать другие, не возвращайте из неё модули и темы (`--code`).
