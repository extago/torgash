## ADR-002. Принцип: библиотеки, а не платформы — решено 2026-08-22

(из §2.1 PLAN.md, дословно; список ниже дополняется по мере того, как
зависимости появляются — каждая с датой и причиной)

Не берём каркасы, диктующие свою архитектуру: **Lunar** (чужое e-commerce ядро — «битрикс-сценарий», используем только как донора идей по схемам цен/каналов), **Filament** (Livewire внутри, второй plugin-API рядом с нашими манифестами, болезненные мажорные апгрейды — вместо него свой тонкий resource-слой на daisyUI+HTMX).

Берём библиотеки с одной зоной ответственности, обёрнутые нашими интерфейсами:

- `spatie/laravel-permission` — RBAC
- `spatie/laravel-medialibrary` — медиа, конверсии размеров, WebP/AVIF
- `brick/money` — деньги в minor units
- `spatie/laravel-sluggable` + своя таблица истории slug — SEO-ЧПУ
- `intervention/image` — обработка изображений
- `bacon/bacon-qr-code` (BSD-2) — QR-код для второго фактора, рендер SVG.
  Добавлена 2026-09-10 (§92 лога). Именно тот случай, о котором этот ADR: одна
  зона ответственности, обёрнута своим `Torgash\Guard\TwoFactor\Qr`. Сам TOTP
  при этом СВОЙ — шестьдесят строк, у которых RFC 6238 печатает тестовые
  векторы, так что библиотеке пришлось бы доверять точно так же; а QR-код это
  Рид-Соломон, восемь масок и таблица версий, то есть две недели с тонкой
  ошибкой внутри. Граница «библиотека или своё» проходит по тому, есть ли у
  задачи печатный ответ на вопрос «правильно ли вышло»

## ADR-003. Данные: ключевые решения — решено 2026-08-22

(из §5 PLAN.md, дословно. Ссылка «см. §9» указывает на `docs/progress/2026-08.md`.)

- **Характеристики товаров — гибрид, две полки (решено 2026-08-22, после
  разведки других движков, см. §9).** Изначальный план "не EAV, всё JSONB" уточнён
  по итогам живого опыта юзера с парсингом/импортом: свалить все
  распарсенные спеки в один глобальный справочник (как в других движках) даёт кучу
  почти-дублей, потому что для многих товаров они по факту индивидуальные.
  Поэтому:
  - **Global features** (таблицы `m_catalog_features` + `_feature_values` +
    `_feature_groups` + `_feature_category`) — управляемый справочник для
    спек, которые реально общие/фильтруемые (Цвет, Бренд, ОЗУ): у фичи есть
    группа, "цель" (filter/variation/info), тип ввода (select/text/number),
    скоуп по категориям. Меньше по объёму, чем у других движков (нет multiselect,
    нет отдельного "внешнего вида"), но та же идея.
  - **`m_catalog_products.features` (JSONB)** остаётся как было — для
    одноразовых, чисто товар-специфичных спек без переиспользования.
    `variation_group`/`variationAxes()` по-прежнему читают именно это поле,
    архитектуру вариаций не трогали.
  - В форме товара в админке обе полки рядом: "Global characteristics"
    (дропдауны/поля по global features) и "Individual attributes" со
    свитчем JSON ⇄ добавляемые поля (идея юзера) для JSONB-поля.
- **Деньги** — integer minor units + код валюты. Никаких float.
- **ID** — bigint identity; публичные — uuidv7 там, где светятся наружу.
- **SEO** — таблица slug'ов с историей (301 при смене), per-язык.
- **Поиск** — Postgres FTS + pg_trgm на старте; интерфейс поиска — за абстракцией,
  чтобы позже подключить векторный (Laravel AI SDK) или Meilisearch модулем.

## ADR-004. Картинки в описании: владение и жизненный цикл — решено юзером 2026-08-24

(из §«Картинки внутри описания» PLAN.md, дословно. Сама фича ещё не сделана —
остальной её план остался в `docs/PLAN.md`. Открытый вопрос «гнать ли сразу в WebP»
там же, не решён.)

**Владение и жизненный цикл (решено юзером):** картинка, загруженная для
описания, живёт **в рамках товара** — удалили товар, ушли и его картинки. Это
ровно то, что даёт media-library, если цеплять их к самому товару отдельной
коллекцией: ничего дополнительно писать не нужно.

## ADR-005. Подписи объявлений — английские строки + файлы перевода — решено юзером 2026-09-24

**Было:** всё, что модуль или тема ОБЪЯВЛЯЕТ (подпись и подсказка настройки,
варианты выбора, пункт меню админки, право, тип блока, зона, вид правила
показа, флаг, сортировка, проверка стража, описание модуля…), писалось картой
`{"en": …, "ru": …}` прямо в коде и в `manifest.json` / `theme.json`. Чтобы
добавить украинский, пришлось бы править несколько сотен мест в чужом коде.

**Стало:** объявление — это АНГЛИЙСКАЯ строка; перевод лежит в
`lang/<язык>.json` владельца (модуля, темы или ядра) с английским текстом в
роли ключа, как у любой строки интерфейса. Новый язык — это новые файлы, код
не трогается. Читает всё одна функция ядра `label_text($label, $locale,
$fallback)`: строку переводит через `__()`, старую карту по-прежнему понимает
(чужой модуль, написанный до этого правила, продолжает работать), а у карты
без нужного языка берёт английский и тоже переводит.

**Не подписи — не трогаем:** содержимое, которое набирает магазин
(названия товаров, заголовки и настройки блоков, в т.ч. `default_blocks` темы,
засеянные строки в миграциях), остаётся переводимым jsonb и читается через
`t()`; `keywords` у пунктов меню и настроек — это слова для поиска на каждом
языке, а не перевод друг друга, поэтому остаются картой.

**Ловушка общего пространства:** все JSON-файлы перевода одного языка
сливаются в ОДНУ таблицу, поэтому одна английская строка может иметь только
один перевод — иначе молча побеждает тот файл, что загрузился последним.
При переходе таких нашлось 76 (из них 67 были и раньше: «Order» читался как
«Порядок» на странице заказа, «Sales» — как «Акции» в меню админки, «in» —
как «дюйм» в поиске). Где смысл один — оставлен один перевод; где разный —
английская строка теперь говорит, какой из смыслов имеется в виду («Sort
order», «Phone code», «Header style»). Держит это тест
`TranslationFilesTest`, найти конфликты — `python tools/i18n-conflicts.py`,
перевести старый модуль — `python tools/i18n-labels.py`.

## Решения, зафиксированные внутри лога прогресса

Эти решения приняты и обоснованы прямо в записях `docs/progress/2026-08.md`;
дублировать их сюда дословно значило бы переформулировать. Указатели:

- **Гибрид global/individual характеристик, вариации не трогаем** — §9, запись
  «Features v2» (2026-08-22) и «исследование живых админок других движков».
- **Купон-коды вместо полного промо-движка** — §9, «купон-коды» (2026-08-22).
- **`torgash.cart` не знает о купонах; расширение чужой страницы хуками** — §9,
  тот же абзац; тот же паттерн — `catalog.product.buy_box`.
- **Аккаунты покупателей — в ядре, не модуль; покупатели и админы на одном guard** —
  §9, «Аккаунты покупателей» (2026-08-22).
- **Группы покупателей — одна % скидка на группу, без матрицы цен** — §9,
  «Группы покупателей + usergroup-цены» (2026-08-22).
- **Локализованные URL (`/ru/...`), дефолтная локаль без префикса; per-request
  регистрация роутов; несовместимо с `route:cache`** — §9, «Тёмная тема… + локализованные URL»
  (2026-08-23), докблок `LocaleResolver`.
- **Метки: единый движок правил без static/dynamic и cron; `Label::applyConditions()`
  — единственный транслятор правил в SQL** — §9, «метки (бейджи товаров)» (2026-08-23).
- **Инвойс без PDF-библиотеки — печатная HTML-страница** — §9, «Документы заказа» (2026-08-22).
- **Бренды — не отдельная сущность, а характеристика `purpose=brand` со своей
  страницей (как принято в других движках)** — §9, «бренды» (2026-08-23).
- **Палитра v2, floating-label → fieldset/legend сайтвайд** — §9,
  «Редизайн v2» (2026-08-23), плюс `docs/DESIGN-REFERENCE.md` §«Палитра».
- **Налоги: флаг `price_includes_tax` на самом налоге, а не режим магазина** — §9,
  запись про налоги; развёрнуто в `CLAUDE.md` §Taxes.
- **Медиа: WebP + качество + размеры миниатюр — настройки модуля `torgash.media`;
  конверсии на загрузке синхронны намеренно** — §9, записи про медиа-модуль;
  `CLAUDE.md` §Commands (Images).
- **Блоки/лейауты: исполняемый код не хранится в БД; зоны — тот же механизм
  `App\Core\Zones`, второго не заводим** — §9, записи про `torgash.blocks`.
- **База данных — локаль ICU `und`, не C (C ломает кириллицу молча)** — §10.10 и
  §10.12 в `docs/progress/2026-08.md`; закреплено в `CLAUDE.md` §Environment.
- **Пакеты локалей: идентичность строки по `ref` (`osm:`/`geonames:`), не по
  коду региона и не по id источника; `previous_ref` для смены источника** —
  §10.18 в `docs/progress/2026-08.md`.
- **Лицензия пакетов из OSM — ODbL 1.0 share-alike + «© OpenStreetMap
  contributors»; на лицензию движка не влияет** — §10.18, там же.
- **Тарифные зоны: одна выигравшая зона по узости; «нет ставки — метод не
  показывается»; ставки строками, а не сериализованным блобом; правило области
  как `UA:12`** — §11.6–§11.7 в `docs/progress/2026-08.md`.
- **Гибкая доставка: отдельный модуль `torgash.shipping`** (зоны + способы
  уезжают из `torgash.checkout`; `checkout` остаётся формой заказа, магазин
  цифровых товаров снимает доставку целиком; `shipping` requires `checkout`,
  шов через хуки; `novaposhta` requires `shipping`). Плюс: три оси способа
  (применимость/цена/фолбэк); условия строками; объёмный вес = `divisor` +
  `charge_on`, а не язык формул (symfony отвергнут); единицы — глоб. настройка,
  хранение в граммах/мм; валюта на ставке; `Shipment[]` в контракте перевозчика,
  мульти-склад — потом; маппинг НП — CSV-снапшот по стабильным `ref`,
  переживающий снятие модуля — §14 в `docs/progress/2026-09.md`, полный план —
  `docs/PLAN.md` §12 (граница модуля — §12.0).
- **Обработка возврата — на ТИКЕТЕ, экрана возвратов нет; деньги — checkout'ский
  `Orders\Refund` (шлюз через `checkout.order.refund`, иначе запись вручную),
  платёж в холде СНИМАЕТСЯ, а не переводится (способность шлюза `void`);
  распоряжение «на склад / списать» — решение при приёмке, а не настройка;
  обмен — новый заказ через `PlaceOrder` с `$as` («от чьего имени»), доплата
  записывается, а не списывается; статус заказа двигается только когда
  возвращать больше нечего и никогда в статус с `inventory_action=increase`** —
  §81 в `docs/progress/2026-09.md`, план — `docs/PLAN.md` §29.4/5.
- **Переписка, привязанная к ЗАКАЗУ, принадлежит `torgash.checkout`, а не
  `torgash.rma`** (вид `order_question`, описание темы, панель на странице
  заказа, маршрут `checkout.enquiry`); возвраты добавляют к панели кнопку и
  блок через `checkout.order.enquiry_actions` / `checkout.order.enquiry_extra`.
  Плюс: **возврат прикрепляется к существующему тикету** (`RequestReturn::
  attach()`) и меняет его вид на `return`, а не заводит второй; правила
  предложения возврата связывают покупателя, но не менеджера — связывает только
  остаток заказа — §82 в `docs/progress/2026-09.md`.
- **Вложения — у ЗАЯВОК, а не у возвратов; загрузка едет тем же POST'ом (своего
  эндпоинта нет), только изображения и только через `ImageProcessor` (тип из
  байтов), диск ПРИВАТНЫЙ + маршрут `enquiries.file` (сотрудник / владелец
  аккаунта / подпись на один файл), отказ по файлу не теряет сообщение** —
  §83 в `docs/progress/2026-09.md`.
- **Восстановление блоков темы — ДЕЙСТВИЕ в админке, а не миграция; экран со
  списком зон, два режима (добавить недостающее по типу+заголовку / заменить
  зону целиком с поимённым перечнем удаляемого); происхождение блока — КОЛОНКА
  `source` (`theme` / NULL), не поле в настройках; правила показа не
  выдумываются** — §84 в `docs/progress/2026-09.md`, план — `docs/PLAN.md` §26.1.
- **`torgash.guard` начат со СБОРА ОШИБОК: слушатель `MessageLogged` (не патч
  скелета), строка на ВИД сбоя со счётчиком (исключение — класс+файл+строка,
  прочее — сообщение с заменёнными цифрами), атомарный `on conflict do update`,
  запись не бросает и не входит повторно, контекст — образец последнего случая
  без самого исключения; «разобрался» прячет, а не удаляет, и снимается новым
  появлением** — §85 в `docs/progress/2026-09.md`, план — `docs/PLAN.md` §25.
- **Капча — часть guard, а не ядра** (ядро даёт только точку `core.form.check`):
  пер-форма, исключения по группам покупателей, провайдером; нужен новый реестр
  имён форм `core.forms` в ЯДРЕ — §25.2/6. **Сделано** — §86 в
  `docs/progress/2026-09.md`: провайдер + реестр `guard.captcha.providers`,
  встроенная арифметическая (текст рендерится в КАРТИНКУ, алфавит — цифры и три
  знака: наивному OCR тяжелее на единицу искажения, человеку читать легче),
  ответ живёт в сессии под ключом «форма + nonce» и работает один раз, картинку
  создаёт ЗАПРОС картинки, сотрудников и доверенные группы не спрашивают, а
  провайдер, который не может работать, падает ОТКРЫТО и говорит об этом на
  экране настроек. Имена форм — новый фильтр `core.forms` в ядре, разметка
  формы — компонент `<x-form-guard>`.
- **Аудит админки — слушатели Eloquent, а не middleware; вооружает только запрос
  под `/admin` и `/api/v2/admin` (консоль и очередь не пишут ничего); пишется ВСЁ
  минус список исключений (обратное fail-closed правил показа — чужой модуль
  должен попадать под аудит, не зная о guard); актёр хранится ссылкой И снимком
  имени, без внешнего ключа; удаление хранит копию строки; секреты маскируются и
  внутри jsonb; потолок на запрос сказан вслух записью `truncated`; кнопки
  удаления на экране НЕТ — записи уходят только по сроку хранения.** Ядро при
  этом получило два объявления о себе — `core.setting.changed` (из
  `SettingsManager`, только при реальном сдвиге значения) и `core.module.changed`
  (из `ModuleManager`) — §88 в `docs/progress/2026-09.md`, план — `docs/PLAN.md`
  §25.2/2.
- **Список заявок по умолчанию ФИЛЬТРУЕТ (открытые), а не показывает всё**;
  состояние — набор галочек, показывающих это умолчание, плюс скрытый маркер
  `status_set`, без которого «снять все галочки» неотличимо от первого захода —
  §87 в `docs/progress/2026-09.md`.
- **Инварианты: движок в guard, а УТВЕРЖДАЕТ тот, кому принадлежат данные**
  (фильтр `guard.invariants`, ответ на который ничего не стоит модулю при
  снятом guard; сам guard везёт только утверждения про данные ядра). Инвариант —
  СОСТОЯНИЕ, а не событие: починенное удаляется само, но только прогоном,
  который видел всё (`truncated` иначе); отдельная таблица состояния проверок,
  чтобы «в порядке» и «никогда не проверялось» не были одним пустым экраном;
  прогон синхронный, потому что кнопка, которой нужен воркер, не делает ничего;
  исключение «здесь всё нормально» живёт на находке и уходит вместе с ней; текст
  находки хранится ключом и параметрами, а не готовой фразой — §89 в
  `docs/progress/2026-09.md`, план — `docs/PLAN.md` §25.2/3.
- **Исполняемый файл в каталоге загрузок — две половины и НИ ОДНОЙ новой
  таблицы: обе объявлены инвариантами.** Доказательство одно — САМОПРОВЕРКА
  (написать `.php` в каталог загрузок, запросить его по HTTP, прочитать ответ;
  две пробы, вторая с двойным расширением; проба удаляется в `finally`); конфиг
  веб-сервера печатается, а не пишется. Сканер проверяет имя ПО СЕГМЕНТАМ и
  PHP-тег внутри, не читает содержимое медиафайлов и НИЧЕГО не удаляет — у
  магазина в переезде там законно лежит чужой скрипт. Свои файлы движка
  исключены, чужой модуль объявляет свои через `guard.files.expected`. Движок
  инвариантов получил `manual` — проверку, которую ночной обход не запускает и
  чьи находки не чистит — §90 в `docs/progress/2026-09.md`, план — `docs/PLAN.md`
  §26.3.
- **Магазин для машин: не второй фронтенд, а те же данные в читаемой форме.**
  `robots.txt` и `llms.txt` СОБИРАЮТСЯ ядром (файл из `public/` удалён — иначе он
  молча перекрывает маршрут), а адреса и разделы приносят владельцы данных через
  `core.robots.disallow` / `core.robots.sitemaps` / `core.llms.sections`.
  Аудитории ДВЕ и решение о них — владельца: ассистент, открывающий страницу по
  просьбе человека, разрешён по умолчанию, обучающий краулер — нет; имена агентов
  хранятся НАСТРОЙКОЙ, а не константой. Любая страница доступна как «тот же адрес
  плюс `.md`», зарегистрированный ПЕРЕД HTML-маршрутом и отдаваемый `text/plain`;
  лимит — свой, ядерный, по адресу. Текст и schema.org печатаются из ОДНОГО
  источника фактов (`Catalog\Seo\ProductFacts`, `publicPrice()` и словесное
  наличие), потому что две машинные формы одного вопроса врозь разъезжаются — и
  разъехались: JSON-LD печатал колонку `price` и сообщал поисковикам цену без
  скидки — §94 в `docs/progress/2026-09.md`, план — `docs/PLAN.md` §26.4.
- **Страницы фильтров живут в КАТАЛОГЕ, а не в `torgash.seo`.** Довод тот же,
  которым §30.3 отправил мета-поля колонками на сущность: это ОПУБЛИКОВАННЫЕ
  адреса. Магазин, снявший SEO-модуль, не должен унести с собой пять тысяч живых
  URL — вместе с модулем уходит написание заголовков, но никогда не сами
  страницы. `torgash.seo` остаётся «шаблоны, экран аудита и alt картинок»: новый
  вид страницы он получает даром, потому что каталог объявляет его через
  `seo.subjects`, и поэтому правила генерации НЕ несут собственного шаблонного
  движка — два движка, пишущих одну и ту же голову, и есть то, что вся эта арка
  убирает.
- **Опубликованный адрес не отзывают.** Генератор ДОБАВЛЯЕТ недостающее,
  обновляет сделанное им самим и выводит похудевшую страницу ИЗ КАРТЫ САЙТА, но
  никогда не из существования: 404 на странице, которую поисковик уже держит, —
  худший из трёх возможных ответов и самый незаметный. Удаление — осознанное
  действие человека, и оно оставляет 301 на категорию. Та же форма, что у
  `Torgash\Blocks\ThemeDefaults`: нажать дважды — значит не сделать ничего
  нового. `noindex` генератор не трогает вовсе — это переключатель магазина, и
  прогон, возвращающий его обратно, спорил бы с админом каждую ночь —
  §99 в `docs/progress/2026-09.md`, план — `docs/PLAN.md` §30.8.
- **Категория — это её подкатегории, везде и без переключателя.** Одно место
  отвечает на «эта категория и всё под ней» — `Torgash\Catalog\Support\
  CategoryTree` (синглтон на запрос, обход в ширину с множеством увиденного,
  чтобы зациклённый `parent_id` не вешал запрос). Родительская страница
  показывает поддерево и ссылается на детей; условия акций, доставки, меток,
  наценок, карточек мотивации и правил показа берут поддерево; пикеры во всех
  шестнадцати экранах идут в порядке дерева с отступами. Случая, где нужно
  другое, придумать не удалось, а лишний переключатель — ещё одна возможность
  настроить неправильно; галочка «incl. subcategories» у меток (разворачивавшая
  ровно на один уровень) убрана, потому что переключатель, который больше
  ничего не решает, хуже отсутствующего. Единственное исключение —
  `FilterRule::with_children`: «в скольких категориях ПОРОЖДАТЬ страницы» это
  решение о том, сколько каталога публиковать, а не о том, что значит категория.
  Швы прежние: доставка о дереве не знает (каталог отдаёт категории строки
  вместе с предками через `shipping.cart_lines`), `torgash.seo` не называет
  классов каталога (у вида страницы появился необязательный `options` — «как эта
  сущность выглядит в пикере», в отличие от `title`) — §100 в
  `docs/progress/2026-09.md`.
- **Адрес фильтра пишется словами, а читается в обоих написаниях.**
  `Torgash\Catalog\Filters\FilterQuery` — одно место на чтение и на запись,
  потому что они обязаны совпадать до буквы. Слово берётся из `Feature.code` +
  `FeatureValue.code` (не `slug`: он UNIQUE ГЛОБАЛЬНО, это адрес страницы
  бренда, а параметру нужна область видимости в пределах характеристики —
  `UNIQUE (feature_id, code)` уже есть). Несколько значений одной
  характеристики — через ЗАПЯТУЮ: группа чекбоксов иначе не умеет, повтор ключа
  оставляет PHP только последнее значение. Старое написание
  `feature[id][]=valueId` читается ВСЕГДА и свободно смешивается с новым — это
  то, что публиковалось до сих пор и что лежит в чужих ссылках; оно же остаётся
  для характеристики или значения без кода. Характеристика, названная как то,
  чем каталог уже владеет (`page`, `q`, `sort`, `price_min`…), слово не
  получает. **Неизвестный код совпадает НИ С ЧЕМ**, а не снимает фильтр: в
  другом написании неизвестный id уже даёт пустую выдачу, и расхождение
  показало бы весь каталог там, где второе написание показывает пустоту; такой
  фильтр называется пилюлей с адресом возврата, иначе пустая страница ничего не
  объясняет. Миграция проставляет коды строкам, появившимся до колонки, — иначе
  функция тихо не работает, пока не пересохранишь каждую характеристику —
  §102 в `docs/progress/2026-09.md`.
