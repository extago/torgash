# Как пользоваться API

Каждый вызов несёт токен и называет ресурс. Форма адреса одна на всё:

    GET    /api/v2/admin/{resource}
    GET    /api/v2/admin/{resource}/{key}
    PATCH  /api/v2/admin/{resource}/{key}
    POST   /api/v2/admin/{resource}/{key}/actions/{action}

**Админка → Справочник API** — живой список: каждый адрес, который есть в этом
магазине, его фильтры, чем он отвечает, и кнопка «Отправить», которая делает
вызов прямо со страницы. То же самое в машиночитаемом виде лежит по адресу

    GET /api/v2/openapi.json

— OpenAPI 3.1, публичный (у клиента, который генерирует заготовку, токена ещё
нет) и собранный из того, что объявили модули, а не написанный рядом. Отдайте
его Postman, генератору кода или тому, кто пишет другую сторону.

## Авторизация

Выпустите токен в админке и отправляйте его в каждом вызове:

    Authorization: Bearer tg_...

Токен принадлежит аккаунту, который его выпустил, и никогда не может больше,
чем может этот аккаунт. Ограничение до `read` — то, что не даёт фиду цен
поменять заказ. Сам токен показывается один раз, при выпуске: база хранит
только хэш, так что украденный дамп нельзя использовать повторно.

## Как обратиться к строке

По нашему id или по любому ключу, который объявил ресурс, — у товара это
`external_id`, `sku` и `slug`. Это один и тот же товар:

    /api/v2/admin/products/4
    /api/v2/admin/products/ST-2002
    /api/v2/admin/products/1c-42

В этом смысл `external_id`: обмен хранит свой id, и ему никогда не нужно
помнить наш.

## Списки

    ?page=2&itemsPerPage=50
    ?order[sku]=desc
    ?updated_after=2026-09-01T00:00:00Z
    ?status=active

Если попросить больше, чем разрешает магазин, придёт потолок, а не ошибка.
`updated_after` — фильтр, на котором стоит строить обмен: выгрузка всего каталога
каждую ночь — верный способ добиться, чтобы интеграцию отключили.

Ответ всегда одной формы:

    {"data": [...], "meta": {"page": 1, "itemsPerPage": 30, "total": 412, "pages": 14}}

## Запись

`PATCH` меняет то, что в нём названо, и ничего больше — отправка остатка не
рискует названием, ценой или описанием. Каждый ресурс сам решает, что может
писать обмен; у товаров это остатки, статус, цены, артикул и `external_id`, но не
адрес страницы, категории или фотографии.

Цены отправляются в основных единицах и могут называть свою валюту:

    PATCH /api/v2/admin/products/1c-42   {"price": 42000, "price_currency": "UAH"}

Хранятся они ровно так, как их сохранила бы форма в админке: введённое число
запоминается, а цена в валюте магазина вычисляется из него (см. документацию
каталога о ценах в другой валюте).

## Как изменить заказ

Не записью в колонку статуса, а просьбой о переходе:

    POST /api/v2/admin/orders/TG-000123/actions/status   {"status": "complete"}

Работает тот же код, что и выпадающий список в админке: двигаются остатки,
изменение записывается в журнал, покупателю уходит письмо. `PATCH` со `status`
выглядел бы так, будто сработал, и не сделал бы ничего из этого.

## Витрина и язык

    X-Storefront: main          (id или код; иначе витрина по умолчанию)
    Accept-Language: ru

Цены, валюты и переводы следуют за этими двумя заголовками.

## Половина магазина

`/api/v2/shop/...` публична, ровно как собственные страницы витрины:

    GET   /api/v2/shop/products?q=ноутбук&category=laptops
    GET   /api/v2/shop/products/ST-2002
    GET   /api/v2/shop/categories

Она отвечает тем, что может видеть посетитель, — товары, которые показываются в
списках, цены через тот же фильтр показа, что и на странице, без себестоимости, —
и писать не умеет: туда проведён только GET.

### Корзина

    POST   /api/v2/shop/carts                     → { "token": "..." }
    GET    /api/v2/shop/carts/{token}
    PATCH  /api/v2/shop/carts/{token}/items       { "product": "ST-2002", "quantity": 2 }
    DELETE /api/v2/shop/carts/{token}

Токен и ЕСТЬ авторизация: храните его — и это ваша корзина. Неизвестный токен —
404: API не говорит, существует ли корзина, тому, кому не дали её адрес.

Один вызов задаёт количество, и `0` удаляет строку: «сколько этого вам нужно» —
один вопрос. Товар называется по id, артикулу или внешнему id, как и везде.

Все суммы — в младших единицах учётной валюты магазина; `currency` в ответе
говорит, в чём показываются цены посетителю.

### Оформление

Браузер отвечает на все вопросы оформления на одной странице и отправляет форму
один раз. Клиент так не может: ему нужно дать адрес, прежде чем узнать стоимость
доставки, и выбрать доставку, прежде чем узнать итог. Поэтому оформление —
разговор с корзиной: каждый ответ хранится на ней, и клиент может прерваться и
вернуться.

    GET    /api/v2/shop/carts/{token}/checkout
    PATCH  /api/v2/shop/carts/{token}/checkout    { "city": "Київ", "place_id": 703448 }
    POST   /api/v2/shop/carts/{token}/checkout/complete

`PATCH` СЛИВАЕТСЯ с уже данными ответами, так что шаг выбора доставки не
стирает адрес. Поле, отправленное как `null`, стирается. С предложением пока
ничего не сверяется: адрес, вводимый по одному полю, какое-то время выглядит
бессмыслицей, и отказ сделал бы форму невозможной.

`GET` отвечает состоянием оформления для уже данных ответов:

    {
      "answers":  { … то, что уже дано … },
      "delivery": [ { "id": "3", "label": "Courier delivery", "cost": 5000,
                      "delivery_time": "1–2 days", "needs_address": true,
                      "needs_fields": false, "meta": {} } ],
      "payment":  [ { "id": 2, "label": "Card online", "charged_in": "UAH" } ],
      "currency": "USD", "subtotal": 4000, "discount": 0
    }

Варианты доставки посчитаны для уже данного адреса — поэтому адрес и есть первый
вопрос. `cost`, равный `null`, означает, что перевозчик ответил, но цену не
назвал: магазин посчитает её вручную, и клиент не должен писать «бесплатно».
`needs_fields` говорит, что варианту нужно что-то ещё от покупателя (отделение,
откуда забирать); `charged_in` — валюта, которую способ оплаты запросит у банка,
когда не может принять ту, в которой идут покупки.

`complete` оформляет заказ. Всё заново выводится из сохранённых ответов, и
клиенту ничего не доверяется, так что вариант доставки без тарифа в выигравшей
зоне купить нельзя, как бы корзину ни патчили. Незаконченное оформление
возвращается как `422` с перечнем полей:

    { "message": "The checkout is not complete.",
      "errors": { "email": ["The email field is required."] } }

а оформленный заказ — как `201`:

    { "data": { "order": { "number": "TG-000123", "status": "awaiting_payment",
                           "total": 4500, "currency": "UAH",
                           "payment": { "state": "unpaid", "currency": "UAH",
                                        "amount": 4500, "url": "https://…" } } } }

`payment.url` — куда браузер был бы перенаправлен: собственная страница шлюза.
Откройте её во встроенном браузере и вернитесь; принять карту без неё нельзя.
`null` — если способ не берёт деньги онлайн.

Заказ оформляет тот же объект, через который проходит форма витрины, поэтому
остатки, статусы, валюты, налоги, автоматизации и письмо с подтверждением ведут
себя здесь точно так же. Корзина очищается, но не удаляется: её токен
по-прежнему на неё указывает.

Тексты сообщений приходят на языке из `Accept-Language`.
