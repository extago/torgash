# Как написать правило

**Продажи → Автоматизации.** Правило — это четыре шага подряд: **когда**
что-то произошло, **подождать**, если нужно, **только если** выполняются
условия, **тогда** действие: написать менеджеру в Telegram, отправить заказ
в другую систему, поставить статус, назначить менеджера.

## Когда

Правило бывает про заказ или — если включён модуль заявок — про заявку.

Про заказ:

* **Заказ размещён** — один раз, при оформлении.
* **В заказе что-то изменилось** — общее. Оно несёт список изменившихся
  полей, поэтому его можно сузить до того, что вам важно: статус, состояние
  оплаты, оплаченная сумма, итог, состав, менеджер, способ оплаты, способ
  доставки, стоимость доставки. Ничего не отмечено — срабатывает на любое
  изменение.
* **Изменился статус заказа** — то, в чём мыслит продавец; оставлено
  отдельно, потому что это самый нужный триггер.

Про заявку (`torgash.enquiries`):

* **Поступила заявка**
* **Покупатель написал снова** — новое сообщение в уже существующей заявке.
* **Сменился статус заявки**
* **Заявка ждёт ответа дольше нормы** — дольше, чем в настройке заявок
  **Отвечать в течение, часов**.

Одно действие админа — одно событие, сколько бы записей в базу оно ни
сделало: правка состава меняет строки, подытог и итог, а правило увидит это
один раз.

## Подождать

**Ждать, мин**, и ждёт очередь — магазин при этом не задерживается. Нужно
для «через полчаса после оформления, если всё ещё не оплачен…». `0` —
сразу (всё равно через очередь).

**Условия проверяются в момент выполнения, а не когда правило сработало.**
За полчаса заказ могли оплатить или отменить, и отправить в него «всё ещё
не оплачен» — единственное, чего не простят.

## Только если

Должны выполняться ВСЕ требования. «Одно из» пишется внутри одной строки:
список статусов — это одно требование, а не три. Правило без требований
выполняется на каждое событие.

Для заказа:

| Условие | Что спрашивает |
|---|---|
| Статус заказа | входит в / не входит в отмеченные статусы |
| Состояние оплаты | входит в / не входит в |
| Сумма заказа | не меньше / не больше |
| Категория товара | содержит товар из / все товары из / не содержит товара из (категория включает свои подкатегории, как и везде в магазине) |
| Способ оплаты, Способ доставки | равно / не равен — название, как оно записано в заказе |
| Страна | один из / ни один из — коды, `UA, PL` |
| Город | равно / содержит |
| Менеджер | кто-то назначен / никто не назначен |
| Купон | применён любой купон / применён этот купон / купон не применялся |

Для заявки: **Тип заявки** и **Статус заявки** (входит в / не входит в),
**Оставлен контакт** (телефон, email, только телефон, из личного кабинета),
**Менеджер** (назначен или нет) и **Что написали** (содержит слово).

Условие, которое больше никто не понимает (его модуль удалили), никогда не
выполняется: правило, срабатывающее на всё, хуже правила, которое не
срабатывает никогда.

## Тогда

Одно действие или несколько, по порядку:

* **Отправить сообщение в Telegram** — «новый заказ» на телефон менеджера.
  См. ниже.
* **Отправить вебхук** — метод, URL, заголовки по одному в строке и тело,
  которое вы собираете из заказа или заявки.
* **Сменить статус заказа** и **Назначить менеджера** — изменения самого
  заказа, см. «Как поделиться правилом и как менять заказ».
* **Сменить статус заявки** и **Назначить заявку менеджеру** — то же для
  заявки.

Действие, которое имеет смысл только для заказа, в правиле про заявку не
предлагается, и наоборот.

Каждая попытка пишется в **Журнал запусков** вместе с тем, что ушло и что
вернулось, — включая получателя, ответившего 4xx: это тот отказ, которого
иначе никто не замечает. Неудачный запрос повторяется дважды, через минуту
и через пять, с тем же `Idempotency-Key`, чтобы на той стороне отличили
повтор от второго заказа. Вебхук несёт и `X-Torgash-Event` — имя события.
Журнал хранится **Хранить журнал запусков, дней** (по умолчанию 30); в
списке правил красным показано, сколько запусков не удалось за последние
24 часа.

## Telegram

1. Создайте бота через @BotFather и скопируйте **Токен бота**.
2. Добавьте бота в чат или группу, куда должны приходить сообщения, и
   напишите туда что-нибудь.
3. Откройте `https://api.telegram.org/bot<токен>/getUpdates` — число после
   `"chat":{"id":` и есть **ID чата** (у группы оно отрицательное).

Токен — это пароль, поэтому Telegram — отдельное действие, а не вебхук с
токеном в URL: он не показывается в форме (пустое поле оставляет
сохранённый), скрыт в журнале запусков и не попадает в экспорт правила.

Сообщение пишется так, как его пишет человек, с переменными ниже.
Работают `<b>`, `<i>` и `<a href="…">`; значения экранируются для HTML,
поэтому имя покупателя с угловыми скобками не сломает сообщение — Telegram
отказывает целиком, если HTML не разбирается. Длиннее 4096 символов
сообщение обрезается: больше Telegram не принимает.

## Как собрать текст и тело

Переменные — `{{ order.number }}`, по точечному пути; редактор перечисляет
их все в разделе **Доступные переменные** — нажмите на переменную, и она
встанет туда, где курсор. Для заказа — номер, статус, ссылка на заказ в
админке, имя покупателя, телефон, email и адрес, суммы, способы доставки и
оплаты. Для заявки — номер, тип, статус, о чём она, что написал покупатель,
сколько он ждёт и ссылка на заявку в админке.

Строки заказа повторяются блоком:

```
{{#order.items}}• {{ item.name }} × {{ item.qty }} — {{ item.line_total_formatted }}
{{/order.items}}
```

или для API:

```
{"lines":[{{#order.items}}{"sku":"{{ item.sku }}","qty":{{ item.qty }}},{{/order.items}}]}
```

Строка знает и свой товар: ссылку на него (`item.url`, для админки —
`item.admin_url`), фото (`item.image_url`), вариацию одной строкой
(`item.variation` — «чёрный, 256 ГБ»), любую характеристику по её коду
(`item.features.COLOR` — код виден в форме характеристики) или все сразу
(`item.features_text`), бренд, вес в граммах и выбранные с ним опции
(`item.options_text`). Сообщение со ссылками на товары:

```
{{#order.items}}• <a href="{{ item.url }}">{{ item.name }}</a> {{ item.variation }} × {{ item.qty }}
{{/order.items}}
```

Два важных момента:

* **Суммы — в минорных единицах**: `order.total` для 150.00 равен `15000`,
  и это то, что нужно API. `order.total_decimal` (`150.00`) — для систем,
  которым нужна строка, `order.total_formatted` (с валютой, так, как
  магазин пишет деньги) — для человека.
* **Значения экранируются для того места, куда идут**: для JSON в вебхуке,
  для HTML в Telegram. Покупатель по фамилии `O"Brien` не сломает ваш запрос.

Это не Blade и код выполнять не умеет: подставляются пути и повторяются
блоки, всё остальное остаётся ровно тем, что вы напечатали.

## Как проверить

Сохраните правило и нажмите **Проверить на последнем**: правило сразу
выполнится на самом новом заказе (или заявке), минуя ожидание. Условия при
этом проверяются, так что пропуск на проверке — тоже правда о правиле.
Результат виден в журнале запусков вместе с телом запроса: это самый
быстрый способ узнать, что получателю нужен `order_id`, а вы шлёте `number`.

## Какие URL будут отклонены

URL пишете вы, а запрос делает сервер — изнутри вашей сети. Поэтому вебхук
может только выходить наружу: `localhost`, приватные диапазоны и
`169.254.169.254` (сервис метаданных облака, выдающий учётные данные любому,
кто спросит изнутри) запрещены, а редиректы не выполняются.

На машине разработчика, который шлёт на локальный приёмник, включите в
настройках модуля **Разрешить запросы на приватные адреса** — и выключите
обратно до того, как эта база станет магазином. **Таймаут запроса, секунд**
(10) — сколько может отвечать получатель; покупатель его не ждёт, но
зависший получатель держит обработчик очереди.
